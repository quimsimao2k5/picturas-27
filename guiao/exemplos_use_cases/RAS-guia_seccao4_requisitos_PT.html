Na aula vão completar a secção 4 do template (RAS-exercicio_1_template_PT-v2.md) a partir do caso de uso que escreveram nas secções 2.1 a 2.8.

Os requisitos não se inventam: extraem-se do caso de uso. Cada requisito tem de vir de um elemento concreto do caso de uso, e cada elemento relevante tem de dar origem a pelo menos um requisito.

Visão geral: 6 passos

Os passos 2 e 3 fazem-se em paralelo sobre a mesma leitura. Os passos 4 a 6 produzem as três tabelas da secção 4. Se a matriz revelar falhas, volta-se ao caso de uso.

Os passos em detalhe

  1. Ler o caso de uso com atenção

    Leiam o caso de uso linha a linha, de preferência em voz alta no grupo. Os requisitos podem estar escondidos em qualquer secção, não só no fluxo principal.

    Secção do caso de usoO que procurar
    Fluxo Principal (2.2)O que o sistema faz em cada passo
    Fluxos Alternativos (2.3)Comportamentos condicionais (“se… então…”)
    Exceções (2.4)Como o sistema reage a erros: mensagens, estado em que fica
    Pós-condições (2.5)O que tem de ser verdade no fim: muitas vezes é um requisito de fiabilidade ou integridade
    Regras de Negócio (2.6)Limites, quotas, formatos: muitas vezes são restrições ou requisitos não funcionais
    Assunções (2.7)Uma assunção sobre o sistema pode esconder um requisito (e.g., “a operação demora < 1 s”)
    Questões em Aberto (2.8)Não são requisitos ainda. Ou decidem e passam a assunção ou regra, ou ficam em aberto

  2. Procurar verbos de ação

    Sublinhem os verbos do caso de uso. Cada verbo de ação é uma pista para uma funcionalidade que o sistema terá de ter.

    Verbo na coluna “Resposta do Sistema”
    O sistema faz algo → “O sistema deve {verbo}…”
    extrair, converter, armazenar, associar, apresentar, validar, notificar, rejeitar
    Verbo na coluna “Ação do Ator”
    O sistema tem de o permitir → “O sistema deve permitir ao {ator} {verbo}…”
    selecionar, submeter, escolher, cancelar, descarregar, confirmar

    Exemplo — caso de uso Gerar Miniatura de um Vídeo:

    OrigemTexto do caso de usoRequisito candidato
    Passo 2 (ator)O utilizador seleciona um vídeo e escolhe Gerar miniaturaO sistema deve permitir ao utilizador registado pedir a geração da miniatura de um vídeo da sua biblioteca.
    Passo 3 (sistema)Extrai o fotograma do instante 00:00:01O sistema deve extrair o fotograma correspondente ao instante 00:00:01 do vídeo selecionado.
    Passo 4 (sistema)Converte o fotograma em JPEG de 320 × 180 pxO sistema deve converter o fotograma extraído numa imagem JPEG de 320 × 180 px.
    Passo 5 (sistema)Associa a miniatura ao vídeo e apresenta-aDois requisitos: um para associar, outro para apresentar (regra da atomicidade, passo 4).

  3. Procurar números, limites e qualidades

    Os requisitos não funcionais (NF) e as restrições raramente aparecem como verbos. Aparecem como:

    • Números e unidades: “< 1 s”, “320 × 180 px”, “máximo 500 MB”, “até 5 operações por dia”.
    • Listas fechadas: “formatos MP4 e MOV”, “apenas perfil premium”.
    • Adjetivos e advérbios: “rápido”, “seguro”, “inalterado”, “sempre” — têm de ser convertidos num valor mensurável.
    Categoria NFPergunta a fazerExemplo para vídeo
    DesempenhoQuanto tempo pode demorar? Quantos pedidos em simultâneo?A submissão deve ser confirmada em ≤ 2 s, independentemente da duração do vídeo.
    Capacidade / limitesQue tamanho, duração ou resolução máximos?O sistema deve rejeitar vídeos com mais de 10 min para o perfil registado.
    CompatibilidadeQue formatos e codecs?O sistema deve aceitar vídeos MP4 (H.264) e MOV.
    Fiabilidade / integridadeO que não pode perder-se ou ser alterado?O ficheiro de vídeo original deve manter-se inalterado após o processamento.
    UsabilidadeO que o utilizador tem de ver ou saber?O sistema deve apresentar a percentagem de progresso, atualizada pelo menos a cada 5 s.
    Segurança / acessoQuem pode fazer o quê?Só o proprietário do vídeo pode pedir o seu processamento.

    Mínimo

    Incluam pelo menos dois requisitos NF ou restrições com alvos mensuráveis.

  4. Escrever cada requisito segundo um padrão

    fixoO sistema deve verboextrair objetoo fotograma do instante indicado condição (opcional)quando o vídeo tiver ≥ 1 s critério (opcional)em ≤ 1 s
    • Usem sempre “O sistema deve…” (ou “deve permitir ao {ator}…”). Evitem “o utilizador pode…” ou “seria bom que…”.
    • Usem os mesmos termos do caso de uso: se no caso de uso é “biblioteca”, não passa a ser “galeria” no requisito.

    Cinco testes de qualidade

    TestePerguntaSe falhar…
    AtómicoDiz só uma coisa?Se tiver “e”, “ou”, “bem como”, provavelmente são dois requisitos: separem.
    VerificávelConsigo descrever um teste que diga “passa” ou “falha”?Falta um valor ou uma condição concreta.
    InequívocoDuas pessoas leriam o mesmo?Retirem palavras vagas: rápido, fácil, intuitivo, adequado, eficiente, user-friendly, “se possível”, “etc.”.
    Sem solução técnicaDiz o quê, e não como?“Usar FFmpeg” ou “guardar em S3” é desenho, não requisito (salvo se for uma restrição imposta).
    RastreávelSei de que parte do caso de uso veio?Ou falta no caso de uso, ou o requisito não pertence aqui.

    Antes e depois

    ❌ Mal escrito✅ MelhorProblema corrigido
    O sistema deve gerar miniaturas rapidamente.O sistema deve gerar a miniatura em ≤ 1 s para vídeos até 1080p.Vago → mensurável
    O sistema deve associar a miniatura ao vídeo e apresentá-la na biblioteca.(1) O sistema deve associar a miniatura gerada ao vídeo de origem.
    (2) O sistema deve apresentar a miniatura do vídeo na biblioteca do utilizador.    		Não atómico → dois requisitos
    O sistema deve tratar erros de vídeo.O sistema deve apresentar a mensagem “Não foi possível ler este vídeo” quando o ficheiro estiver corrompido, sem alterar o estado do vídeo.Genérico → condição e comportamento concretos
    O sistema deve usar FFmpeg para extrair fotogramas.O sistema deve extrair o fotograma correspondente a um instante indicado do vídeo.Solução técnica → necessidade

    Preencher as colunas da tabela 4.1

    ColunaComo preencher
    IDREQ-VID-{FUNC}-{nnn}, e.g. REQ-VID-TRIM-001. Um ID nunca se reutiliza, mesmo que o requisito seja apagado.
    RequisitoUma frase, segundo o padrão acima.
    TipoF (funcional) ou NF, indicando a categoria: NF (Desempenho), NF (Fiabilidade), …
    PrioridadeDeve ter (sem isto o MVP não funciona) · Deveria ter · Poderia ter. Num MVP, a maioria dos requisitos centrais é “Deve ter” — mas não todos.
    Novo/AltNOVO: funcionalidade que não existia. ALT: altera algo que já existe no PictuRAS (perfis, quotas, encadeamento, lote, exportação…).
    OrigemO elemento do caso de uso: Passo 3, FA1, Exceção 2, RN2, Pós-condição de sucesso… Pode haver mais do que um.
    Como verificarO teste ou critério de aceitação, numa frase: dado… quando… então…

  5. Identificar o impacto no sistema existente · tabela 4.2

    O PictuRAS já existe. Para cada requisito marcado como ALT — e para os NOVO que tocam em mecanismos atuais — perguntem:

    • Mexe nos perfis (anónimo / registado / premium) ou na quota de operações? Um vídeo conta como 1 operação ou como N fotogramas?
    • Entra no encadeamento de ferramentas ou no processamento em lote?
    • Afeta a exportação, o armazenamento ou a biblioteca do utilizador?

    Para cada elemento afetado, decidam: Manter (fica igual), Estender (passa a fazer mais) ou Alterar (muda o comportamento atual), e indiquem os requisitos relacionados.

    Exemplo

    A RN4 do exemplo de vídeo (“a geração de miniatura não conta para a quota diária”) dá origem a um requisito ALT, porque muda a regra atual de contagem de operações → impacto Alterar sobre “Limite de 5 operações/dia (perfil registado)”.

  6. Cria a matriz de rastreabilidade e verifica a cobertura · tabela 4.3

    1. Listem na primeira coluna todos os elementos do caso de uso: cada passo, fluxo alternativo, exceção, regra de negócio e pós-condição.
    2. Na terceira coluna, indiquem os requisitos que lhe correspondem.
    3. Façam as duas verificações:
      • Nenhum requisito órfão: cada requisito da tabela 4.1 aparece pelo menos uma vez na matriz.
      • Nenhum elemento por cobrir: cada elemento relevante tem pelo menos um requisito. Se um passo não tem requisito, justifiquem (e.g., passo puramente do ator, sem resposta do sistema).

    Exemplo — caso de uso Gerar Miniatura de um Vídeo:

    Elemento do caso de usoRequisito(s)
    Passo 3REQ-VID-THUMB-001
    Passo 4REQ-VID-THUMB-002
    RN1REQ-VID-THUMB-001
    RN2REQ-VID-THUMB-002
    Pós-condição de sucessoREQ-VID-THUMB-003

    Retorno ao caso de uso

    Se encontrarem um requisito sem origem, há duas hipóteses: falta um passo ou regra no caso de uso (atualizem as secções 2.x) ou o requisito não pertence a este caso de uso (retirem-no).

Lista de verificação da secção 4

  • Todos os verbos de ação do caso de uso foram analisados.
  • Cada requisito segue o padrão “O sistema deve…”.
  • Todos os requisitos são atómicos, verificáveis e sem palavras vagas.
  • Cada requisito tem ID único, Tipo, Prioridade, Novo/Alt, Origem e Como verificar.
  • Pelo menos dois requisitos NF ou restrições, com valores mensuráveis.
  • Exceções e fluxos alternativos também deram origem a requisitos.
  • Tabela de impacto preenchida para os requisitos ALT e mecanismos existentes afetados.
  • Matriz sem requisitos órfãos nem elementos do caso de uso por cobrir.
  • Se o caso de uso foi corrigido durante a derivação, a versão do documento foi atualizada.
